Tumor Diagnosis: a Tool4Boxology walkthrough

Dr. Ana: "I want something simple in my head. Show the system enough tumors I already diagnosed, so it learns what I look for. Then let it check new scans the same way and tell me why, so I can compare its reasoning to mine."
Marco: "That is really three things. First we define the labels and the data: labels are the meaning we want to capture, and data is the example input we train on. Then we train a model, and later we apply it to a new scan."
Dr. Ana: "Right, but the why matters most to me. I do not just want an answer. I want to see the reasoning so I can check it against my own judgment."
Marco: "Then we should not train a plain black-box model. We should use a neural-symbolic setup, so the system can learn from examples but still keep the reasoning traceable."
Marco: "Tool4Boxology gives us a unified visual language for that workflow. We draw the labeling, training, and deduction blocks, check validation live, and make sure the system stays explainable instead of just predictive."
Dr. Ana: "And if I connect something wrong?"
Marco: "The tool checks it live. If the label does not match what training expects, or the trained model does not match what deduction needs, it flags it immediately — before either of us writes code."
What you're looking at

Three composed patterns, one pipeline

Tumor Diagnosis chains three design patterns end to end — the output of each one is the input to the next:

  • Labeling — an Expert (Actor) performs Engineering to produce Label for Segments (Symbol). A human expert manually engineers ground-truth labels.
  • Train a Supervised Model — those labels plus Preprocessed MRT Data (Data) go through Train to produce a Supervised Model (Model).
  • Symptom Detection — a new MRT Image (Data) and the trained Supervised Model go through Deduce to produce a Diagnosis (Symbol).

That's the point of drawing it in Boxology rather than a generic flowchart: each step is named by its epistemic role — engineering, training, deducing — so the kind of neuro-symbolic integration is explicit and, as the next steps show, checkable.

Reading the shapes

The shape legend

  • Triangle — an Actor (a person or agent), e.g. Expert.
  • Solid rounded rectangle — a Process, e.g. Engineering, Train, Deduce.
  • Solid rectangle — Data, e.g. Preprocessed MRT Data, MRT Image.
  • Dashed green rectangle — a Symbol, e.g. Label for Segments, Diagnosis.
  • Dashed hexagon — a Model, e.g. Supervised Model.
  • Grey rounded group — one design pattern: Input(s) → Process → Output.
The pipeline

From diagram to knowledge discovery — five steps

The same five steps apply to any design you build in Tool4Boxology, not just this one.

Validate every pattern

Tool4Boxology doesn't just check that boxes are connected — Check Boxology checks each pattern's Input(s) → Process → Output triple against the legal typed combinations defined in the T4B ontology. Running it on Tumor Diagnosis confirms all three patterns:

  • Engineer: [Actor] -> [Symbol]
  • Train: [Symbol, Data] -> [Model]
  • Deduce: [Data, Model] -> [Symbol]

Because every stage matches a recognised pattern, the whole diagram is a well-formed neuro-symbolic system — a symbolic labeling step, a neural training step, and a hybrid inference step, wired together correctly — not just a plausible-looking flowchart.

Check Boxology confirms Labeling, Train a Supervised Model, and Symptom Detection are all valid.

Turn it into a knowledge graph

Once a diagram validates, Tool4Boxology's RML pipeline turns it into RDF triples using the T4B vocabulary. Each pattern becomes a t4b:DesignPattern connected to its process, inputs, and outputs (t4b:hasProcess, t4b:hasInput, t4b:hasOutput), and the whole diagram becomes a top-level system — here, Tumor-Diagnosis — connected to its three patterns via t4b:hasPattern. Nothing about the design is lost: the same Labeling / Train a Supervised Model / Symptom Detection structure now exists as data you can query.

Query the graph with SPARQL

The editor ships a SPARQL panel with ready-made example queries (Find output nodes, List Boxologies and Pattern Counts) plus a free-form editor. Say you want to know which pattern in Tumor Diagnosis actually produced Label for Segments — ask the graph directly:

PREFIX t4b: <http://tool4boxology.org/>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
SELECT * WHERE {
  ?pattern t4b:hasOutput ?OutPut;
    rdfs:label ?patternLabel.
  ?OutPut rdfs:label "Label for Segments" .
}

Run Query returns exactly one row — the pattern that produced that output:

patternOutPutpatternLabel
…/DesignPattern/group_1783160823186…/Component/node_17831606554893"Labeling"

You can also query the inputs and outputs of any pattern, find all patterns in a system, or discover which systems use a specific pattern. This makes it much easier to explore existing neuro-symbolic architectures and reuse proven design patterns when building new AI systems.

Explore it — and check node status — in the KG Viewer

The KG Viewer renders the whole graph as an explorable node-link diagram: Tumor-Diagnosis at the centre, connected to its three patterns, which fan out to their inputs, outputs, and processes. Clicking any pattern node re-runs the same validity check from Step 1, live, on that node — its Type, a VALID/INVALID Status, the matched validation pattern, and its inputs and outputs. Clicking Train a Supervised Model shows:

  • Status: VALID
  • Validation Pattern: Symbol-Data>Train>Model
  • Inputs (2): Label for Segments, Preprocessed MRT Data
  • Outputs (1): Supervised Model

If you edit the diagram later and accidentally break a pattern — say, remove one of its inputs — this is where you'd see it flip to invalid.

The full Tumor-Diagnosis graph in the KG Viewer, with one pattern selected.

Generate documentation for a one-page overview

Generate Documentation (in the KG Viewer toolbar) turns the whole graph into a plain-text summary you can save and share: a system description, the pipeline order, and every pattern with its process and inputs/outputs. For Tumor Diagnosis, it reads roughly like this:

# Automatic System Documentation

## Tumor-Diagnosis

### System Description

The system collects Expert, Label for Segments, Preprocessed MRT Data,
MRT Image, Supervised Model, performs an ordered pipeline of
transformations and inference steps (Labeling: engineers system
artifacts; Train a Supervised Model: trains a model; Symptom
Detection: infers symbolic outputs), and produces Label for Segments,
Supervised Model, Diagnosis.

### Example Pipeline

Engineering -> Train -> Deduce

### Design Patterns

1. Labeling
   - Process: Engineering
   - Inputs: Expert
   - Outputs: Label for Segments
2. Train a Supervised Model
   - Process: Train
   - Inputs: Label for Segments, Preprocessed MRT Data
   - Outputs: Supervised Model
3. Symptom Detection
   - Process: Deduce
   - Inputs: MRT Image, Supervised Model
   - Outputs: Diagnosis

That's a full, accurate overview of the system — generated from the graph, not written by hand — good for a README, a paper appendix, or onboarding a teammate who's never seen the diagram.
